# Langfuse v3 → v4 migration plan

## Context

Langfuse is deployed via the `langfuse/langfuse-k8s` Helm chart (`1.5.40`, app `3.221.1`) in four environments: prod, preview, dev, and dev-tenant (`modules/astro-infra/terraform/environments/{prod,preview,dev}/langfuse.tf`, `modules/astro-infra/terraform/modules/dev-tenant/langfuse.tf`). All four use external ClickHouse (Altinity operator), external Postgres (RDS in prod/preview, in-cluster in dev), external Redis, and S3/MinIO blob storage. No EE license is configured.

Langfuse v4 replaces the ClickHouse `traces`/`observations` tables with a unified `events_full` table plus an `events_core` materialized view, and deprecates the v1 read/ingestion APIs in favor of v2/v3 equivalents. Two Astro integrations reach past Langfuse's stable public surface and are directly affected:

- `apps/astro-server/internal/langfuse/provisioner.go` writes directly to Langfuse's Postgres (`organizations`, `projects`, `api_keys`) to provision projects and API keys, bypassing the EE-gated admin API.
- `apps/astro-server/internal/langfuse/client.go` calls legacy read endpoints (`/api/public/traces`, `/api/public/traces/{id}`, `/api/public/observations/{id}`, `/api/public/scores`, `/api/public/metrics`, `/api/public/metrics/daily`, `/api/public/dataset-items`, `/api/public/v2/datasets`).

**Correction to an earlier version of this doc:** `docs/01-spec/insights-rollup-spec.md` and its producer (`apps/astro-server/handlers/insights_rollup_producer.go`) do **not** query ClickHouse directly — an earlier draft of this doc claimed they did, which was wrong. The producer calls `client.GetMetrics()`, i.e. Langfuse's public Metrics API (`view: "traces"` / `view: "observations"`), exactly like every other `GetMetrics` call site. The spec's "traces view" / "observations view" language refers to that API's `view` parameter, not literal ClickHouse database views queried directly — the confusion came from the spec's own design-verification methodology (it reads Langfuse's *source code*, `packages/shared/src/features/query/{dataModel,queryBuilder}.ts`, to understand what the public Metrics API can group by), which is research methodology, not this codebase's runtime behavior. Astro's actual architectural principle — never bypass a system's stable API to query its internal store directly — is already followed here, correctly.

## Migration approach

Three-step process per the official guide (infra → server → data model), staged per environment, dev first.

### Phase 0 — infra readiness (done, files only)

- Bump ClickHouse server to `26.4` (recommended; previous `25.12` was the bare v4 minimum) — done in all four environments' files.
- Confirm RDS Postgres and ElastiCache Redis versions meet v4 minimums (Postgres 16 recommended, Redis 7.2 recommended) — not yet checked.
- No Helm chart version bump needed beyond the routine `1.5.41` patch bump — keep `clickhouse.deploy: false`, change only the app image tag.

### Phase 1 — dev + dev-tenant, `legacy` mode (skipped)

The plan called for applying `legacy` mode first and validating deployment mechanics (probe timings, heap sizing — see the removed "v3.2x cold start" comments) before touching write mode. In practice, dev and dev-tenant files went directly to `dual` (see Current status above) without an intermediate applied-and-validated `legacy` step. If dev/dev-tenant apply surfaces boot or probe failures, this is the first place to suspect, since the mechanics were never isolated from the write-mode change.

### Phase 2 — rewrite the coupled integrations

In progress. Do this before any environment moves to `events_only` — `dual` mode tolerates `client.go`/insights-rollup still reading v3 tables, but `events_only` does not:

- `client.go`: **done and confirmed live** (see risk table above for the per-method breakdown and the `fields=` correction). Design: `Client` holds a `traceReader` interface (`v3Reader` or `v4Reader`), selected once in `NewClient` from `LANGFUSE_USE_V4_API` — not re-checked per call, and not threaded through `NewClient`'s signature, so none of its ~20 call sites or tests needed touching. `v3Reader` is the default: `LANGFUSE_USE_V4_API` is an opt-in, and only an explicit true value selects `v4Reader`, so each environment cuts over on its own once its Langfuse writes in `dual` mode. `v3Reader` and `v4Reader` are two separate, clearly delineated implementations of the same interface (`getTraces`, `getTraceDetail`, `getTraceCore`, `getObservation`, `getMetrics`, `getDailyMetrics`); both embed a shared `transport` (the Basic-auth HTTP plumbing, unchanged from before). Retiring v3 later means deleting `v4Reader`'s block and its branch in `NewClient` (or the reverse, if v4 turns out to need the retirement) — one type and one constructor branch, not scattered per-method checks. (This replaced an earlier version of the design that checked `os.Getenv` inline in every dispatching method — moved to the interface after review.)
- `insights-rollup-spec.md` / `insights_rollup_producer.go`: **does not need a ClickHouse rewrite — it was never querying ClickHouse (see correction above).** It calls `client.GetMetrics()`, so it inherits `client.go`'s v4 support automatically once `LANGFUSE_USE_V4_API=true`. Three issues found by reading the actual caller against the v4 rewrite, all resolved: the mixed count+cost query bug is fixed; cross-span `tags`/`userId` attribution is confirmed safe against real production data; the `userId`-grouping row_limit ceiling (max 1000, confirmed live, confirmed unavoidable at the API level) has the best available mitigation shipped (order by leading measure descending), with a narrow, accepted residual gap for accounts genuinely exceeding 1000 daily active users — see the risk table for the exact accepted trade-off.
- `provisioner.go`: no change required; confirmed schema-compatible.

### Phase 3 — dev, `dual` → `events_only`

Dev and dev-tenant files are already set to `dual` (Current status above); applying them starts this phase. Monitor the worker health endpoint (`GET /api/health?failIfEventPropagationStuck=true`) once applied. Do not cut to `events_only` until Phase 2 lands — `client.go` and insights-rollup need the new read paths working before the old tables stop being written.

### Phase 4 — dev-tenant, preview, prod

Repeat legacy → dual → events_only per environment, in that order. Prod is reachable cross-cluster via PrivateLink (`privatelink-langfuse.tf`); no PrivateLink-specific changes are needed, but watch the internal NLB health checks during pod cutover.

### Phase 5 — cleanup

Only after confirming historic data is visible in `events_full`/`events_core` in a given environment:

```sql
TRUNCATE TABLE traces;
TRUNCATE TABLE observations;
```

Irreversible. Do this last, per environment, after a verification pass — not as part of the cutover itself.

**Important operational finding, not just an API detail:** `/v2/observations` and `/v2/metrics` return `"only available in a Langfuse v4 write mode"` (404) in `dual` mode when `LANGFUSE_MIGRATION_V4_ALLOW_PREVIEW_OPT_IN=false`. This is not a `dual`-mode limitation — it's this specific flag, which we'd set to `false` (the doc's own conservative default, hiding the v3→v4 UI toggle and the v2 APIs for all users while dual-writing). Setting it to `true` unblocks the v2 API surface while staying in `dual` mode with the old tables still fully written — no need to cut over to `events_only` to validate the rewrite. Dev and dev-tenant now run with this flag `true`.

### Correction: root detection, found by preview traffic

The rewrite passed `isRootObservation` as a dedicated query param. `/v2/observations` silently ignores dedicated params and honors only the JSON `filter=` array, so the listing returned every span and each child span appeared to be its own trace. This is the same defect class already recorded in this doc for `tags=` and `orderBy=`, and the same one Langfuse fixed upstream for `sessionId=` (issue #15636).

Sent as a filter entry, `{"type":"boolean","column":"isRootObservation","operator":"=","value":true}` works correctly on both `/v2/observations` and `/v2/metrics` in 4.11.0. Verified live: an unfiltered trace query returned 3 rows and the filtered one returned only the root, and a `/v2/metrics` count returned 53 unfiltered against 3 root-scoped. Langfuse resolves the column to `(parent_span_id = '' OR is_app_root)`, so it covers both a physical root and an application root whose parent was never ingested.

An earlier draft of this section claimed the filter matched nothing because ingestion never sets `is_app_root`. That was inferred from a column table belonging to a different surface and is wrong. Upstream had already fixed logical-root exposure in #15567 (public API) and #15633 (metrics), both released before 4.11.0. A null filter on `parentObservationId` also works but covers only the physical-root case, so the flag is preferred.

Two further defects surfaced with it, both real:

- **`fields` omitted the tags callers authorize against.** `GetLangfuseTraceDetail` rejects a trace whose tags lack the caller's deployment, so an empty tag list turned into a 404 on every trace. Tags live in the `trace_context` group; the default is `core,basic` only. `CreatedAt` was unset for the same reason, which rendered as an invalid date.
- **Trace cost was read from the root span.** Cost sits on child `GENERATION` spans and does not roll up, so the root reports zero. Measured on four real traces: 0 on the root against roughly $0.0128 summed. Langfuse tracks this gap for its own list views in issue #16077, still open, where trace-level cost is likewise unavailable.

The lesson is narrower than the earlier draft suggested: the v4 API is stricter about *where* a filter goes, not broken in what it can express. Test a predicate through the real endpoint before concluding the API cannot do it.

**Status: `client.go` is fully implemented and confirmed live**, end to end, via a real Go program calling every rewritten exported method (`GetTrace`, `GetTraceCore`, `GetObservation`, `GetMetrics` both views, `GetDailyMetrics`, `GetTraces`, `GetQueueTraces`) against the dev adhoc instance with `LANGFUSE_USE_V4_API=true`, not just curl against the raw endpoints. `insights_rollup_producer.go` inherits this automatically (it's a `client.GetMetrics()` caller, not a ClickHouse caller) and its three additional issues (mixed-measure bug, `userId` row_limit, cross-span attribution) are all resolved — two fixed in code, one confirmed a permanent, mitigated API constraint, one confirmed a non-issue against real production data. Nothing identified in this migration is currently blocking a cutover to `events_only` on technical grounds alone; the remaining work is applying preview/prod and validating there.

## Rollback

During `legacy` or `dual` mode, the old ClickHouse tables keep receiving all data, so rolling back to v3 is safe. Historic backfill only reads from the old tables, never modifies them. Once an environment cuts to `events_only`, new data lands exclusively in the new tables — rollback past that point risks losing data written after cutover.
