# docs/ — what lives where, and how it stays current

This file is the index. If you're deciding where a new doc goes, or which doc
to trust for an area, start here.

## What each folder is for

| Folder | Contents | Lives long-term? |
|---|---|---|
| `00-RFC/` | Formal spec proposals for external-facing formats (package spec, deployment spec, agent card spec). | Yes — these are the spec of record until superseded by a new RFC. |
| `01-spec/` | Feature specs: the intended design for something, written close to when it was built. | Mostly. A spec can drift from what shipped; treat it as intent, and check `03-architecture` for the as-built version when one exists. |
| `03-architecture/` | As-built system design: how something actually works today, not how it was planned. (Previously split across `03-architecture/` and `05-architecture/` from an earlier renumbering that never finished; merged into one folder.) | Yes — these are meant to track the running system and should be corrected when they drift, not left as history. |
| `04-guides/` | How-to guides for a recurring task (local dev, a library's conventions, a release process). | Yes. |
| `05-implementation/` | Implementation notes for specific features. (Previously split across `02-implementation/` and `05-implementation/`; merged into one folder — the number is a leftover from that history, not a meaningful ordering.) | Mixed — some are living references, some are point-in-time notes from a project that's since shipped and moved on. |
| `06-plan/` | Proposals for something not yet built, or only partly built. | No, by design. Once a plan ships, it becomes history: either fold what's still true into an architecture doc and delete the plan, or leave the plan in place with a one-line "superseded — see X" banner at the top so it doesn't get read as current. Don't rewrite a plan doc into an architecture doc in place; the two have different jobs. |
| `07-feedback/` | Retrospective notes, evaluation write-ups, and the [doc-drift-log](07-feedback/doc-drift-log.md) (known documentation/code drift not yet worth a dedicated pass). | Yes, as a log. |
| `08-incidents/` | Postmortems. One file per incident, never edited after the fact. | Yes, as history. |
| `09-reference/` | Reference material for a third-party system's own contract (payload shapes, API quirks) that doesn't belong to any one feature. | Yes. |
| `changelog/` | One file per PR/branch, required by CI. Append-only history of *what changed and why*, not a living description of *how the system works now*. Never edited after merge. | Yes, as history — never consolidated in place. |
| `releases/` | Public + internal release notes, one file per release. Append-only. | Yes, as history. |

## The rule

**An architecture, guide, or reference doc (`03`, `04`, `09`) describes the
system as it is now.** If code you're changing disagrees with one of these,
the doc is wrong and gets fixed as part of the same change — not filed as a
follow-up, unless the fix needs domain knowledge the current change doesn't
have (in which case, log it in
[`07-feedback/doc-drift-log.md`](07-feedback/doc-drift-log.md) rather than
letting it go unrecorded).

**A spec or a point-in-time implementation note (`00`, `01`, and the
point-in-time half of `05`, per the folder table above) is a design record,
not a live description.** It can legitimately drift from what shipped;
treat it as intent, the same way the folder table already says to. Fixing
one of these when it disagrees with code doesn't mean rewriting it to match
current behavior. It means bannering it: say plainly what changed or what
superseded it, and point at the doc that now describes the as-built system,
usually a `03-architecture` doc. The disagreement still can't be left
unmarked, only what "fixed" looks like differs from the paragraph above.

**Every `03-architecture/` doc carries `**Status:**` and `**Last verified:**`
near the top.** Either order works, and either can follow the H1 title
instead of opening the file (most docs do it that way); only presence is
enforced, not position. A doc with no stamp hasn't been through this yet.

Last verified is the date someone last actually checked the doc's claims
against code, whether or not that check changed anything — update it any
time you verify the doc, not only when you edit it.

Status is a real per-doc call, not a rubber stamp. "Authoritative —
describes the shipped system" is correct when you believe the *whole* doc,
not just the section you were reading. If you know part of it is thinner or
more volatile than the rest — the code changes daily and hasn't settled,
one section covers a feature that's mid-build, a subsystem got a short
overview instead of a full pass — say that precisely instead of writing
"Authoritative" and hoping the caveat buried in the prose is enough (e.g.
"Authoritative, but volatile — see the doc's own '...' section before
trusting a specific detail," or "Authoritative for X; Y is covered only
briefly"). A field where every doc says the same thing can't inform a
decision — it only earns its place by actually varying when a doc warrants
it.

**A `changelog/` entry describes what one PR did and why.** It's never
updated after the fact, even if the design it describes later changes —
that's what the *next* changelog entry and the architecture doc's own edit
are for.

**Prefer editing over creating.** Before adding a new doc, check whether an
existing one under `01-spec` or `03-architecture` already covers the area and
update that instead. A second doc describing the same system is exactly how
this tree drifts: two files that both need updating, and only one that gets
touched.

## Area → canonical doc map

The starting point for "which doc do I trust for X." This grows as areas get
verified; an area not listed here hasn't been checked yet, not confirmed
accurate.

The **Code paths** column is read by the docs-map hook
(`.claude/hooks/docs-map-check.mjs`) as well as by a human — it's the same
table, not a second copy of the mapping. Keep path globs specific enough
that an edit to them really does mean "this area changed," or the hook just
becomes noise.

The **Verify** column is the fastest command that actually exercises this
area's code, not just compiles it — run it after a change instead of
assuming green typecheck means correct behavior, per the Development
Workflow's "verify for real" step. `go test` commands assume `cd
apps/astro-server` unless another directory is given. A command scoped to a
package with zero test files still runs, harmlessly (`go test` reports "no
test files") — that's not a lie, but it isn't verifying anything either;
worth noticing if you see it. **Never put a literal `|` in a Verify command**,
even inside backticks: a bare `|` breaks this table's columns in some Markdown
renderers (a code span doesn't reliably protect it), and an escaped `\|`
copy-pastes into a shell as a literal backslash, silently matching zero tests
while `go test` still exits 0 — confirmed both ways the hard way. Chain
multiple `go test -run X` commands with `&&` instead of writing one `-run
'X|Y'`; run every command you write here for real before adding it.

## How this stays current

A Claude Code skill (`docs-map`, see `.claude/skills/docs-map/`) reads this
file's area map to pull only the relevant docs into context for a task,
instead of an agent guessing which of 90+ files to open. A session-level hook
checks, when a task under a mapped code path finishes, whether the mapped
doc was also touched, and prompts a check if not. Neither replaces judgment
about what changed — both exist so the check actually happens instead of
depending on someone remembering.

Three CI checks back this up for anything that reaches this repo outside a
Claude Code session (a human PR, a different tool): `scripts/check-doc-links.mjs`
and `scripts/check-doc-stamps.mjs` both run on every PR touching `docs/**`
(the former fails on a broken relative link or dangling symlink, the latter
fails a PR if any `03-architecture/` doc is missing its Status/Last-verified
stamp), and `scripts/check-doc-freshness.mjs` runs on a weekly schedule (not
per-PR, since it reports cumulative drift, not one diff) and flags any area
whose mapped code paths have commits newer than its doc's Last-verified
date. The freshness check never blocks a merge; a flagged doc means "worth
a look," not "known wrong."

None of the above catches a doc that's simply wrong, as opposed to stale —
a claim that was never true, or one that rotted silently in an area nobody
touched recently enough to trip the freshness check. Two more mechanisms
target that: `agents.md`'s Development Workflow calls for verifying a doc's
specific load-bearing claim against current code before leaning on it to
override what's in front of you (cheap, and it fires exactly when a wrong
claim would otherwise do damage), and
[`04-guides/doc-honesty-audit.md`](04-guides/doc-honesty-audit.md) is a
quarterly adversarial backstop for whatever that misses. Both feed
`07-feedback/doc-drift-log.md`, tagged with how each finding was actually
caught — the only way to eventually tell which of these channels is
carrying its weight.
