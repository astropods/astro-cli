# Redeploy Support — Backend

## Summary

Adds proper redeploy support: a new pre-filled template endpoint returns all deployment values (including KMS-decrypted secrets), and the deploy endpoint now accepts `target.deployment_id` for in-place updates that preserve the deployment ID and namespace.

## Design

**Spec change:** Removed `target.namespace` from `DeploymentTarget` (server-owned, flows through `ApplierConfig.Namespace`). Added `target.deployment_id` for clients to signal an in-place update.

**New endpoint** `GET /api/v1/agents/:account/:name/deployment-template/:deploymentID` generates a template pre-filled with the existing deployment's display name, account, variable values (secrets decrypted via KMS envelope), and interface adapters.

**Deploy update path:** When `target.deployment_id` is set, the deploy endpoint looks up the existing active deployment, reuses its namespace and ID, and calls `UpdateDeploymentFull` which updates the row in-place and cascade-deletes/re-inserts normalized data within a single transaction.

**New store methods:** `GetDeploymentVariables` reads stored variables (with encrypted values and nonces). `UpdateDeploymentFull` updates an existing deployment row and re-creates normalized data atomically.

See [docs/05-implementation/redeploy-support.md](../05-implementation/redeploy-support.md) for the full design spec.

## Migration

No database migration required. The `namespace` field removal from the spec type is backward-compatible — existing stored specs with `namespace` in JSON will be ignored on unmarshal (Go's `omitempty` + missing struct field). Clients should stop sending `target.namespace` and may start using `target.deployment_id`.
