# Per-adapter scoping for the authorization owner-fallback

## Summary

A deployment configured with only `slack` grants silently locked down its `web` adapter for everyone — including members of the deployment's owning account. The reverse held too: declaring a `web` grant denied `slack` access to the owner.

The owner-account fallback in `apps/astro-server/handlers/authorization.go` was meant as a transitional shim for pre-rollout deployments that had never written a grant. It checked "does this deployment have *any* grant rows" and turned itself off the moment one row existed, regardless of which adapter the row was for. So writing the first grant on one adapter implicitly switched every other adapter to deny-by-default with no warning and no spec entry to point at.

## Design

Scope the fallback per-adapter. `authorizationstore.HasAnyGrants` now takes an `adapter` argument and adds it to the `WHERE` clause; `tryOwnerFallback` forwards the request's adapter into the lookup.

```go
// before
hasAny, err := authStore.HasAnyGrants(deploymentID)

// after
hasAny, err := authStore.HasAnyGrants(deploymentID, adapter)
```

Semantics after the change:

- A deployment with `slack: [anyone]` and no `web` grants has the fallback **on for web**: members of the owning account reach the web adapter, and `anyone:slack` continues to apply on slack.
- A deployment with explicit `web` grants and no `slack` grants has the fallback **on for slack**: bot/owning-account candidates pass through the slack adapter.
- A deployment with explicit grants on a given adapter (any subject type, any number of rows) has the fallback **off for that adapter** — the spec is the complete picture for that surface.

The fallback's identity-resolution side is unchanged: it still requires a candidate that matches the deployment's owning account, and slack candidates still naturally include that owner so legacy slack flows keep working.

## Migration

None required. The change is strictly additive for deployments that were locked out by the old "any grant disables every fallback" behavior — they regain owner-account access on the unconfigured adapter. Deployments with explicit grants on every adapter are unaffected.
