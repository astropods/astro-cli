# Centralized Audit Logging System

## Summary

There was no way to answer "who did what, when, and what changed" across the platform. Deployment status transitions were tracked in `deployment_events`, but user actions on accounts, members, agents, and other resources had no persistent trail. This change adds a centralized audit logging system that records every mutation with actor, action, resource, and optional before/after metadata — powering both admin visibility and the deployment `updated_at`/`updated_by` fields the frontend already expected.

## Design

A single `audit_logs` table stores account-scoped entries with actor identification, action classification, resource targeting, and flexible JSONB metadata for diffs. No PII (email) is stored — actor display info is resolved by user ID at query time.

**Core package** (`internal/auditlog/`): `Store` provides `Log` (synchronous insert), `LogAsync` (fire-and-forget goroutine), `Query` (cursor-paginated via `created_at < $before`), and `LatestPerResource` (batch `DISTINCT ON` query returning most recent timestamp + actor per resource). Nil-safe — `LogAsync` on a nil store is a no-op, so handlers work in tests without a database.

**Integration pattern**: explicit `auditStore.LogAsync(log, evt)` calls inside each mutation handler, not middleware. Middleware can't capture resource IDs, action semantics, or before/after state. Each handler builds an `Event` via `FromGinContext(c, accountID)` (pre-fills actor/IP/UA) then sets action, resource, and metadata. Admin gRPC methods use `ForAdmin(accountID, identity)` and are distinguishable by `actor_type='admin'`.

**Coverage**: 27 HTTP handlers (accounts, members, invitations, agents, deployments, avatars) and 8 admin gRPC methods (delete/restart/stop/wakeup/rollback deployment, rename account, approve/deny quota).

**Query endpoint**: `GET /api/v1/accounts/:account/audit-log` with filters for `resource_type`, `resource_id`, `action`, `actor_id`, cursor pagination via `before` timestamp, and configurable `limit` (default 50, max 200). Account admin permission required.

**Deployment updated_at/updated_by**: `ListDeployments` batch-queries `LatestPerResource("deployment", ids)` to resolve the most recent audit entry per deployment in a single SQL round-trip. The `AgentDeployment` response gains `updated_at` and `updated_by` fields. Frontend falls back to `created_at` when no audit history exists yet.

## Migration

- Schema: `CREATE TABLE audit_logs` with four indexes (account+time, account+resource+time, actor+time, time). Additive, no existing tables modified.
- Existing deployments will show no `updated_at` until their first audited mutation occurs — frontend uses `created_at` as fallback.
- No breaking API changes. The new `updated_at`, `updated_by` fields on the deployment list response and the `/audit-log` endpoint are purely additive.
