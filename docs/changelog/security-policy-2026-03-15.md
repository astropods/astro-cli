# Apply Restricted Pod Security Standard to All K8s Manifests

## Summary

All K8s workloads generated by astro-server previously had no security context set, running with writable root filesystems, full capabilities, and default service account tokens. This wires the existing `hardenPodSpec()` and `hardenContainer()` helpers into every manifest builder to satisfy the Kubernetes "restricted" Pod Security Standard.

## Design

The `security.go` helper file already defined `hardenPodSpec()` and `hardenContainer()` but they were never called. This change adds a single call to each at the end of every manifest builder:

- **Pod-level** (`hardenPodSpec`): `runAsNonRoot: true`, `runAsUser: 1000`, `fsGroup: 1000`, `seccompProfile: RuntimeDefault`, `automountServiceAccountToken: false`, shared `/tmp` emptyDir volume.
- **Container-level** (`hardenContainer`): `runAsNonRoot: true`, `runAsUser: 1000`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`, `/tmp` VolumeMount.

Hardening is applied in `BuildDeployment`, `buildContainer`, `buildMessagingContainer`, `buildCollectorContainer`, `BuildStatefulSet`, `BuildJob`, `BuildIngestionDeployment`, and `BuildCronJob`. Since manifests are rebuilt from scratch on every deploy/reconciliation, no database changes or migration are needed — security context is always re-applied.

## Migration

No action required. All new and redeployed workloads automatically receive the restricted security context. Existing running pods will pick up the changes on their next redeploy or reconciliation cycle.
