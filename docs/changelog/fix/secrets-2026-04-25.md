## Summary

Secret variables updated via the `PUT /api/v1/accounts/:account/variables/:varName` endpoint were stored with an unconditional base64 encoding even when KMS encryption was not configured. This caused the raw base64 string to reach the container as the environment variable value instead of the original plaintext.

## Design

The root cause was a divergence between the create and update code paths. The create handler correctly branched on whether KMS was available — encrypting and base64-encoding when a KMS key was configured, or storing plaintext when it was not. The update handler always called `base64.StdEncoding.EncodeToString` on the output of `encryptVariableValue` regardless of whether encryption had occurred, so without KMS the plaintext was base64-wrapped with no corresponding decode on read.

The fix replaces both inline implementations with a shared `applyValue` helper:

```go
func applyValue(v *accountvars.AccountVariable, plaintext string, enc *envelope.Encryptor) error {
    if v.Secret && enc != nil {
        ciphertext, nonce, err := enc.Encrypt([]byte(plaintext))
        ...
        v.Value = base64.StdEncoding.EncodeToString(ciphertext)
        v.Nonce = nonce
    } else {
        v.Value = plaintext
        v.Nonce = nil
    }
    return nil
}
```

Both create and update now call `applyValue`, which owns the single rule: base64(ciphertext) with a nonce when KMS is present, plaintext with nil nonce otherwise. The old `encryptVariableValue` function is removed.

## Migration

No action required. Existing secrets stored with the incorrect base64 encoding will need to be re-saved (via update or re-create) to correct their stored value.
