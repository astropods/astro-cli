# Deployment FGA resource lifecycle

## Summary

Connect the FGA operations introduced previously to the deployment lifecycle. Each new organization deployment now becomes a WorkOS `deployment` resource, its creator receives `deployment-editor` on that resource, renames stay synchronized, and undeploying removes the resource and its assignments. This establishes reliable authorization data before Astro begins enforcing FGA decisions.

## Design

Astro remains authoritative for whether a deployment exists. Creation stores the authenticated Astro user as `deployed_by` and records the desired WorkOS state in the same database transaction as the deployment. After commit, a background worker resolves that user to their organization membership, registers the deployment resource, and assigns `deployment-editor`. Missing membership mappings receive bounded fast retries followed by hourly assignment retries while the creator remains a current member. This assignment-only marker does not block account purge and is cleared when the creator is absent or has left the organization. Personal accounts and installations without WorkOS configured bypass FGA intent and jobs.

The local synchronization record is a durable reconciliation ledger, not an entitlement table. It stores desired and applied resource state, a version for race-safe name updates, and retry diagnostics; WorkOS remains authoritative for readers, editors, groups, and permission decisions. The ledger is also the single applicability gate: it knows whether FGA is enabled, records work only for organization deployments, and tells each lifecycle caller whether a job is needed. WorkOS failures do not roll back successful deployments. Immediate jobs minimize propagation delay, while the periodic sweep enqueues the same unique per-deployment jobs so WorkOS mutations cannot race each other.

Undeploy records the desired `deleted` state alongside the final deployment status, then deletes the WorkOS resource with cascading assignment cleanup. Account purge waits for this cleanup to converge. If the organization has already been removed from WorkOS, reconciliation verifies that absence and treats its child-resource cleanup as complete rather than blocking purge forever. Deletion also converges when the local WorkOS organization ID is unavailable because there is no safe external cleanup request Astro can make. This change uses resource registration, name updates, role assignment, and resource deletion; it does not yet call the FGA check operation, filter deployment lists, expose collaborator APIs, or return FGA-based `403` responses.

## Review guide

1. **Start with the contracts:** PR2 put the WorkOS organization membership ID in the session and established the external permission slugs `deployment:read` and `deployment:edit`. PR3 added the small, generic FGA interface and WorkOS SDK adapter for resources, assignments, and checks. PR4 uses those primitives for the first time and adds resource-name updates; it does not authorize requests yet.
2. **Follow the durable intent:** The schema and deployment store record `deployed_by` plus the desired WorkOS resource state in the same transaction as the deployment change. The reconciliation row is an outbox-style ledger—desired/applied versions and retry diagnostics—not a local copy of readers, editors, groups, or permission decisions.
3. **Trace the create path:** After an organization deployment commits, a best-effort job registers `deployment:<deployment-id>` beneath the WorkOS organization and assigns its creator `deployment-editor`. A failure in WorkOS never rolls back the valid Astro deployment; the ledger remains pending so reconciliation can safely repeat the idempotent operations.
4. **Check delayed membership handling:** If the creator is still an organization member but their WorkOS membership mapping has not arrived, registration still succeeds. The role assignment gets bounded fast retries and then hourly repair attempts. A missing or departed creator stops assignment repair, and assignment-only work never blocks account purge.
5. **Trace rename and deletion:** Changed names advance the desired version; same-name PATCH requests do not enqueue FGA work. All WorkOS mutations run through one unique job per deployment. Undeploy records deletion intent, then removes the WorkOS resource with cascading assignment cleanup; if the organization is already gone, or its local WorkOS ID is unavailable, the ledger converges instead of blocking purge. Lifecycle cleanup—not a delayed creator-role assignment—is what account purge waits for.
6. **Confirm the boundaries:** The synchronization store owns the enabled and organization-only checks and returns whether durable work was recorded. Personal deployments and WorkOS-disabled installations therefore write no intent and enqueue no FGA jobs. Immediate jobs provide the fast path, while the periodic sweep repairs missed enqueues and transient failures through that same serialized path.
7. **Understand what comes next:** PR5 adds live WorkOS decisions in shadow mode without changing user-visible access. PR6 uses the same ledger to backfill historical deployments. Enforcement, collaborator/group APIs, accessible-resource discovery, and FGA-driven `403` responses remain later PRs.

## Migration

Apply the declarative database schema before deploying the server. The target WorkOS environment must contain the `deployment` resource type beneath organization, permissions `deployment:read` and `deployment:edit`, and roles scoped to the **Deployment** resource type: `deployment-reader` with read and `deployment-editor` with read and edit. Organization owner/admin roles inherit both permissions; the baseline member role receives neither. No client or API migration is required.
