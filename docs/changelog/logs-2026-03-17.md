# Loki-backed Deployment Logs

## Summary

Deployment log fetching previously pulled directly from live Kubernetes pods via the CoreV1 API. This was dangerous (requires broad K8s RBAC), ephemeral (logs vanish when pods are evicted), and not scalable. Alloy already ships all pod logs to a centralized Loki instance — this change routes log queries there instead.

## Design

A new `internal/loki` package provides a lightweight HTTP client around Loki's `/loki/api/v1/query_range` API. Logs are indexed by Alloy with four labels: `namespace`, `pod`, `container`, and `cluster`. Since each deployment gets a unique namespace (`astro-<compact-id>-0`), the minimum viable LogQL selector is:

```logql
{namespace="astro-abc123-0"}
```

Pod and container filters are appended when provided, making `pod` optional for the first time — callers can now retrieve logs from all pods in a deployment in a single request.

Both the HTTP handler (`GET /api/v1/deployments/:id/logs`) and the admin gRPC method (`AdminService.GetPodLogs`) use Loki when the `LOKI_URL` env var is set, and fall back to direct K8s pod log streaming otherwise. This allows a zero-downtime rollout.

New query parameters on the HTTP endpoint:
- `pod` — now optional (previously required)
- `since` — RFC3339 or Unix nanoseconds; defaults to 1 hour ago
- `until` — RFC3339 or Unix nanoseconds; defaults to now

New fields on `GetPodLogsRequest` proto:
- `since_unix_ns` — optional start time
- `until_unix_ns` — optional end time

The Loki NLB (port 3100) already accepts queries from prod/preview VPCs — no infra changes are needed for the endpoint. The only infra change required is setting `LOKI_URL=http://<loki-nlb-dns>:3100` in the astro-server deployment.

## Migration

Set `LOKI_URL` in the astro-server deployment to the Loki NLB DNS (already computed as `loki_nlb_dns` in `terraform/environments/prod/helm.tf`). Without it, the server falls back to the existing K8s pod log behavior with no behavior change.
