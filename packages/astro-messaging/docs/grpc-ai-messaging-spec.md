# gRPC AI Messaging Architecture Specification

## Overview

This spec defines a gRPC-based architecture for astro-messaging that natively supports AI features across all messaging platforms (Slack, Discord, Teams, etc.). The design replaces the current HTTP `/message` endpoint with bidirectional gRPC streaming for real-time AI interactions.

## Problem Statement

### Current HTTP Implementation Limitations

1. **No Native Streaming**: Polling-based message updates inefficient for AI responses
2. **Limited AI Features**: Cannot support loading states, typing indicators, suggested prompts
3. **Poor Real-time Performance**: HTTP request/response cycle adds latency
4. **Slack AI Gaps**: Missing `assistant.threads.setStatus`, streaming, suggested prompts
5. **No Bidirectional Communication**: Agent cannot receive mid-stream updates or cancellations
6. **Rate Limiting Challenges**: 3-second Slack update limit conflicts with smooth streaming

### Why gRPC for AI Messaging

1. **Bidirectional Streaming**: Real-time agent responses with platform feedback
2. **Efficient Protocol**: Binary encoding reduces overhead vs JSON
3. **Strong Typing**: Protocol buffers ensure consistency across services
4. **Built-in Features**: Deadlines, cancellation, metadata propagation
5. **Multi-language**: Works with Python, Node.js, Go agents
6. **Multiplexing**: Single connection for multiple concurrent conversations

## Architecture

### High-Level Flow

```
User (Slack/Discord/Teams)
    ↓
Platform Adapter (WebSocket/Events)
    ↓
Messaging Service Sidecar (Thin gRPC Server)
    ↓ [Bidirectional gRPC Stream]
Agent Container (gRPC Client + Business Logic)
    ↓
AI/LLM Processing
```

### Component Responsibilities

**Messaging Service (Sidecar)**:
- **Thin adapter layer** - NOT a heavy business logic service
- gRPC server exposing `AgentMessaging` service
- Platform adapters translate native events ↔ proto messages
- Handles platform-specific rate limiting
- **Light caching** of recent context (LRU cache, not authoritative)
- Manages platform credentials
- Streams agent responses back to platforms

**Agent Container (Source of Truth)**:
- gRPC client connecting to messaging service
- **Owns conversation context and history**
- Processes messages with AI/LLM
- Streams responses in real-time
- Sends status updates (thinking, searching, etc.)
- Requests suggested prompts, thread titles
- Stores conversation data persistently if needed

**Platform Adapters (In Messaging Service)**:
- Translate platform events → proto messages
- Translate proto responses → platform API calls
- Handle platform-specific features (Slack's `setStatus`, Discord embeds)
- Manage rate limiting per platform requirements
- **No business logic** - pure protocol translation

## Protocol Buffer Definitions

### Core Message Types

**Design Principle**: Pure protocol translation. These messages contain only what's needed to route and identify the message. Agent owns all conversation logic.

```protobuf
syntax = "proto3";
package astro.messaging.v1;

import "google/protobuf/timestamp.proto";

option go_package = "github.com/postman/astro/messaging/v1;messagingv1";

// Message from user to agent (platform → agent)
message Message {
  // Identity (who, when, where)
  string id = 1;                          // UUID generated by messaging service
  google.protobuf.Timestamp timestamp = 2;

  // Platform identification
  string platform = 3;                    // "slack" | "discord" | "teams"
  PlatformContext platform_context = 4;   // Platform-specific IDs and metadata

  // User who sent the message
  User user = 5;

  // Message content
  string content = 6;                     // Cleaned text (mentions resolved, etc.)
  repeated Attachment attachments = 7;

  // Conversation routing
  // Messaging service provides this for correlation only
  // Agent is responsible for loading/storing actual conversation history
  string conversation_id = 8;             // Stable ID across message lifecycle
}

// Platform-specific context (adapter populates this)
message PlatformContext {
  // Required: Core platform IDs
  string message_id = 1;                  // Original platform message ID
  string channel_id = 2;                  // Channel/room/chat ID
  optional string thread_id = 3;          // Thread/reply chain ID

  // Optional: Display names
  optional string channel_name = 4;
  optional string workspace_id = 5;       // Slack workspace, Discord guild, etc.

  // Platform-specific data
  // Examples: Slack ts, Discord snowflake, Teams activity ID
  map<string, string> platform_data = 10;
}

// User information
message User {
  string id = 1;                          // Platform-specific user ID
  string username = 2;                    // Display name or handle
  optional string avatar_url = 3;
  optional string email = 4;              // If available

  // Platform-specific user data
  map<string, string> user_data = 5;
}

// Attachment from user message
message Attachment {
  enum Type {
    TYPE_UNSPECIFIED = 0;
    IMAGE = 1;                            // jpg, png, gif, webp
    FILE = 2;                             // Generic file
    VIDEO = 3;                            // mp4, mov, etc.
    AUDIO = 4;                            // mp3, wav, etc.
    LINK = 5;                             // URL preview/embed
  }

  Type type = 1;
  string url = 2;                         // Direct download URL (authenticated)
  string filename = 3;
  optional int64 size_bytes = 4;
  optional string mime_type = 5;

  // Optional metadata for rich attachments
  optional string title = 6;
  optional string description = 7;
  optional int32 width = 8;               // For images/videos
  optional int32 height = 9;
}
```

### AI-Specific Types

**Design Principle**: Agent streams responses with AI features. Messaging service translates to platform APIs.

```protobuf
// Agent's streamed response (agent → platform)
// Agent can send multiple AgentResponse messages in a stream
message AgentResponse {
  string conversation_id = 1;             // Matches incoming Message.conversation_id
  string response_id = 2;                 // Stable ID for this response (for updates)

  oneof payload {
    StatusUpdate status = 3;              // "Thinking...", typing indicator
    ContentChunk content = 4;             // Actual message content (streamed)
    SuggestedPrompts prompts = 5;         // Quick reply suggestions
    ThreadMetadata thread_metadata = 6;   // Thread title, creation
    ErrorResponse error = 7;              // Error during processing
    RequestContext context_request = 8;   // Request cached context (optional)
  }
}

// AI status indicators (loading states, typing)
// Platform translation:
// - Slack: assistant.threads.setStatus
// - Discord: typing indicator via bot.send_typing()
// - Teams: typing indicator via sendTypingIndicator()
message StatusUpdate {
  enum Status {
    STATUS_UNSPECIFIED = 0;
    THINKING = 1;                         // Generic "thinking"
    SEARCHING = 2;                        // RAG/knowledge base search
    GENERATING = 3;                       // LLM generation in progress
    PROCESSING = 4;                       // Tool execution
    ANALYZING = 5;                        // Data analysis
    CUSTOM = 10;                          // Custom status with message
  }

  Status status = 1;
  optional string custom_message = 2;     // Used with CUSTOM or overrides default
  optional string emoji = 3;              // Platform emoji (e.g., ":robot_face:")
}

// Streamed message content
// Flow: START → DELTA(s) → END
message ContentChunk {
  enum ChunkType {
    CHUNK_TYPE_UNSPECIFIED = 0;
    START = 1;                            // Create message, returns platform message_id
    DELTA = 2;                            // Append/update content (streamed tokens)
    END = 3;                              // Finalize message
    REPLACE = 4;                          // Full content replacement (edit)
  }

  ChunkType type = 1;

  // Content handling based on type:
  // START: Full initial content (may be empty for immediate presence)
  // DELTA: Incremental text to append (LLM tokens)
  // END: Final text (if any last content) + attachments
  // REPLACE: Complete new content (overwrites existing)
  string content = 2;

  // Attachments sent with END chunk or standalone
  repeated ResponseAttachment attachments = 3;

  // Platform message ID (returned after START, used for updates)
  optional string platform_message_id = 4;

  // Options for message creation
  optional MessageOptions options = 5;
}

// Attachments in agent responses (richer than user attachments)
message ResponseAttachment {
  oneof attachment_type {
    ImageAttachment image = 1;
    FileAttachment file = 2;
    CardAttachment card = 3;             // Rich cards (Slack blocks, Teams adaptive cards)
    LinkPreview link = 4;
  }
}

message ImageAttachment {
  string url = 1;                         // Public URL or data URI
  optional string alt_text = 2;
  optional string title = 3;
  optional int32 width = 4;
  optional int32 height = 5;
}

message FileAttachment {
  string url = 1;
  string filename = 2;
  optional string mime_type = 3;
  optional int64 size_bytes = 4;
}

message CardAttachment {
  string platform_card_json = 1;          // Platform-specific JSON
  // Adapters translate: Slack Block Kit, Discord Embeds, Teams Adaptive Cards
}

message LinkPreview {
  string url = 1;
  optional string title = 2;
  optional string description = 3;
  optional string image_url = 4;
}

// Message creation options
message MessageOptions {
  bool ephemeral = 1;                     // Only visible to user
  bool create_thread = 2;                 // Start new thread
  optional string reply_to_message_id = 3; // Reply to specific message
  bool silent = 4;                        // No notification
}

// Suggested quick replies (Slack AI, Teams suggested actions)
// Platform translation:
// - Slack: assistant.threads.setSuggestedPrompts
// - Teams: suggestedActions in bot response
// - Discord: Custom buttons (component interactions)
message SuggestedPrompts {
  message Prompt {
    string id = 1;                        // Unique ID (for tracking selection)
    string title = 2;                     // Button/chip label
    string message = 3;                   // Full message sent when selected
    optional string description = 4;      // Tooltip/help text
  }

  repeated Prompt prompts = 1;            // Max 4-6 depending on platform
}

// Thread management (create, update title)
message ThreadMetadata {
  optional string thread_id = 1;          // Platform thread ID (if updating)
  optional string title = 2;              // Thread title/subject
  bool create_new = 3;                    // Create new thread
}

// Error response from agent
message ErrorResponse {
  enum ErrorCode {
    ERROR_CODE_UNSPECIFIED = 0;
    RATE_LIMIT = 1;                       // Agent hit rate limit
    CONTEXT_TOO_LONG = 2;                 // Context exceeds LLM limit
    INVALID_REQUEST = 3;                  // Malformed request
    AGENT_ERROR = 4;                      // Internal agent error
    TOOL_ERROR = 5;                       // Tool execution failed
    PLATFORM_ERROR = 6;                   // Platform API error
  }

  ErrorCode code = 1;
  string message = 2;                     // User-facing error message
  optional string details = 3;            // Technical details (logged, not shown)
  bool retryable = 4;                     // Can user retry?
}

// Agent requests thread hydration from adapter
message ThreadHistoryRequest {
  string conversation_id = 1;
  int32 max_messages = 2;                 // How many recent messages (default: 50)
  bool include_edited = 3;                // Include edit history (default: true)
  bool include_deleted = 4;               // Include deleted markers (default: false)
}

message ThreadHistoryResponse {
  string conversation_id = 1;
  repeated ThreadMessage messages = 2;
  bool is_complete = 3;                   // False if truncated due to max_messages
  google.protobuf.Timestamp fetched_at = 4;
}

message ThreadMessage {
  string message_id = 1;                  // Platform message ID
  User user = 2;
  string content = 3;                     // Current content (after edits)
  repeated Attachment attachments = 4;
  google.protobuf.Timestamp timestamp = 5;

  // Edit tracking
  bool was_edited = 6;
  optional string original_content = 7;   // Content before edits
  optional google.protobuf.Timestamp edited_at = 8;

  // Deletion tracking
  bool is_deleted = 9;
  optional google.protobuf.Timestamp deleted_at = 10;

  // Platform-specific data
  map<string, string> platform_data = 11;
}
```

### Platform Feedback

**Design Principle**: User actions on agent messages flow back to agent for bidirectional communication.

```protobuf
// Feedback from user interactions (platform → agent)
// Used in bidirectional streaming for real-time agent updates
message PlatformFeedback {
  string conversation_id = 1;
  optional string response_id = 2;        // Which agent message this relates to
  google.protobuf.Timestamp timestamp = 3;

  oneof feedback {
    StreamControl stream_control = 4;     // Stop/pause generation
    PromptSelection prompt_selection = 5; // User clicked suggested prompt
    MessageReaction reaction = 6;         // Thumbs up/down, emoji reaction
    ButtonClick button_click = 7;         // Interactive button clicked
    MessageEdit message_edit = 8;         // User edited a message
    MessageDelete message_delete = 9;     // User deleted a message
  }
}

// Control agent streaming/generation
message StreamControl {
  enum Action {
    ACTION_UNSPECIFIED = 0;
    STOP = 1;                             // Stop generating
    PAUSE = 2;                            // Pause (resume later)
    RESUME = 3;                           // Resume paused generation
    REGENERATE = 4;                       // Regenerate last response
  }

  Action action = 1;
  optional string reason = 2;             // Why stopped (user click, error, etc.)
}

// User selected a suggested prompt
message PromptSelection {
  string prompt_id = 1;                   // Matches SuggestedPrompts.Prompt.id
  string prompt_message = 2;              // Full message being sent
}

// User reacted to agent message
message MessageReaction {
  enum ReactionType {
    REACTION_TYPE_UNSPECIFIED = 0;
    THUMBS_UP = 1;
    THUMBS_DOWN = 2;
    CUSTOM_EMOJI = 3;
  }

  ReactionType type = 1;
  optional string emoji = 2;              // For CUSTOM_EMOJI
  bool added = 3;                         // true = added, false = removed
}

// User clicked interactive button (from CardAttachment)
message ButtonClick {
  string button_id = 1;                   // Button identifier from card
  optional string value = 2;              // Button value/payload
  string action = 3;                      // Action identifier
}

// User edited a previous message
message MessageEdit {
  string message_id = 1;                  // Platform message ID that was edited
  string new_content = 2;                 // New content after edit
  optional string original_content = 3;   // Original content (if available)
  google.protobuf.Timestamp edited_at = 4;
}

// User deleted a previous message
message MessageDelete {
  string message_id = 1;                  // Platform message ID that was deleted
  google.protobuf.Timestamp deleted_at = 2;
}
```

## Context Management Strategy

### Separation of Concerns

**Platform Thread History** (Adapter's Responsibility):
- Stores recent **platform-specific thread messages** (e.g., last 50 Slack messages in thread)
- Ground truth for "what's currently in the Slack thread"
- Handles edits, deletions, reactions from platform
- Provides hydration: Agent can request current thread state
- Cache duration: Hours (platform data that can be refreshed)
- **Why**: User can edit/delete messages in Slack; agent needs accurate view

**Conversation Context** (Agent's Responsibility):
- Maintains AI conversation state (RAG, memory, session variables)
- Stores semantic context and derived information
- Decides what context to use for AI processing
- Persists long-term conversation data (DB, vector store, etc.)
- **Why**: Agent knows best what context matters for AI

### The Edit/Delete Problem

```
Scenario: User edits message in Slack
1. User sends: "What's the weather?"
2. Agent processes and responds
3. User EDITS to: "What's the weather in Paris?"
4. User sends follow-up: "And tomorrow?"

Without thread storage:
- Agent thinks conversation is about general weather
- Agent responds incorrectly ❌

With thread storage:
- Agent requests thread hydration from adapter
- Adapter returns current Slack thread (with edit)
- Agent sees "What's the weather in Paris?"
- Agent responds correctly ✅
```

### Architecture

```
┌─────────────────────────────────────────────────┐
│  Messaging Service Adapter                      │
│                                                  │
│  Thread History Store (Platform-specific)       │
│  ┌────────────────────────────────────────┐    │
│  │ conversation_123:                       │    │
│  │   - msg_1: "What's the weather?"       │    │
│  │     (edited: "...in Paris?")           │    │
│  │   - msg_2: "Sunny and warm!"           │    │
│  │   - msg_3: "And tomorrow?" (latest)    │    │
│  └────────────────────────────────────────┘    │
│                                                  │
│  Can fetch from Slack API if cache miss         │
└─────────────────────────────────────────────────┘
                    ↕ gRPC
┌─────────────────────────────────────────────────┐
│  Agent                                           │
│                                                  │
│  Conversation Context (AI-specific)              │
│  ┌────────────────────────────────────────┐    │
│  │ conversation_123:                       │    │
│  │   - user_intent: "weather_query"       │    │
│  │   - location: "Paris" (from RAG)       │    │
│  │   - preferences: {...}                 │    │
│  │   - tool_results: [weather_api_data]   │    │
│  └────────────────────────────────────────┘    │
│                                                  │
│  Requests thread hydration when needed          │
└─────────────────────────────────────────────────┘
```

### Why This Design?

1. **Platform accuracy**: Adapter has ground truth for platform thread state
2. **Agent flexibility**: Agent decides what context matters for AI
3. **Handle edits/deletes**: Only adapter can track platform changes
4. **Efficient**: Agent only fetches thread when needed (not every message)
5. **Clean separation**: Platform concerns ≠ AI concerns

### Context Flow Examples

#### New Message Flow
```
1. User sends message in Slack thread
2. Adapter stores message in thread history
3. Adapter sends proto.Message to agent via gRPC
4. Agent calls GetThreadHistory() for context
5. Adapter returns recent Slack thread (with edits)
6. Agent processes with accurate thread context
7. Agent updates its own AI context storage
8. Agent streams response back
```

#### Edit Flow
```
1. User edits message in Slack
2. Slack sends message_changed event
3. Adapter updates thread history (mark edited)
4. Adapter sends PlatformFeedback(MessageEdit) to agent
5. Agent invalidates cached context
6. User sends next message
7. Agent calls GetThreadHistory() (fresh data needed)
8. Adapter returns thread with edited content
9. Agent processes with correct context
```

#### Cache Miss / Hydration Flow
```
1. Agent calls GetThreadHistory(conversation_id)
2. Adapter checks thread_store cache
3. Cache miss or stale (>5 minutes old)
4. Adapter calls Slack API: GetConversationReplies()
5. Slack returns last 50 messages in thread
6. Adapter parses and stores in thread_store
7. Adapter returns ThreadHistoryResponse to agent
8. Agent uses for context
```

### What Messaging Service Should and Should NOT Do

**DO** (Messaging Service Responsibilities):
- ✅ Translate platform events to proto messages
- ✅ Translate proto responses to platform API calls
- ✅ **Store recent platform thread history** (edits, deletes, reactions)
- ✅ Provide thread hydration API for agent
- ✅ Handle platform-specific rate limiting
- ✅ Cache conversation_id mappings (short TTL)
- ✅ Manage platform credentials
- ✅ Stream responses efficiently
- ✅ Fetch thread from platform API when cache miss

**DO NOT** (Agent's Job):
- ❌ Store AI conversation context (RAG, memory, session state)
- ❌ Inject AI-derived context into messages
- ❌ Attempt to understand conversation semantics
- ❌ Make decisions based on conversation content
- ❌ Implement RAG, memory, or AI logic
- ❌ Persist long-term conversation data
- ❌ Implement complex business logic routing

### Key Distinction

| Concern | Adapter | Agent |
|---------|---------|-------|
| **Platform thread messages** (what's in Slack) | ✅ Stores | Uses for context |
| **Edits & deletes** | ✅ Tracks | Receives via hydration |
| **User reactions** | ✅ Captures | Receives as feedback |
| **AI context** (RAG, memory) | ❌ Doesn't store | ✅ Owns |
| **Conversation semantics** | ❌ Doesn't interpret | ✅ Understands |
| **Long-term persistence** | ❌ Short cache | ✅ Responsible |

## gRPC Service Definition

```protobuf
service AgentMessaging {
  // Bidirectional streaming for real-time AI conversations
  rpc ProcessConversation(stream ConversationRequest)
      returns (stream AgentResponse);

  // Server streaming for simple request/response with streaming reply
  rpc ProcessMessage(Message)
      returns (stream AgentResponse);

  // Get current thread history from platform (handles edits/deletes)
  // Agent calls this to hydrate accurate thread state
  rpc GetThreadHistory(ThreadHistoryRequest)
      returns (ThreadHistoryResponse);

  // Optional: Query cache for conversation metadata (not full history)
  rpc GetConversationMetadata(ConversationMetadataRequest)
      returns (ConversationMetadataResponse);

  // Health check
  rpc HealthCheck(HealthCheckRequest)
      returns (HealthCheckResponse);
}

message ConversationMetadataRequest {
  oneof identifier {
    string conversation_id = 1;
    PlatformIdentifier platform_id = 2;
  }
}

message PlatformIdentifier {
  string platform = 1;              // "slack", "discord", "teams"
  string channel_id = 2;
  optional string thread_id = 3;
}

message ConversationMetadataResponse {
  string conversation_id = 1;
  string platform = 2;
  string channel_id = 3;
  optional string thread_id = 4;
  google.protobuf.Timestamp last_message_time = 5;
  int32 message_count = 6;          // Approximate from cache
  bool found = 7;                   // Whether conversation exists in cache
}

message ConversationRequest {
  oneof request {
    Message message = 1;
    PlatformFeedback feedback = 2;
  }
}

message HealthCheckRequest {}

message HealthCheckResponse {
  enum Status {
    UNKNOWN = 0;
    HEALTHY = 1;
    DEGRADED = 2;
    UNHEALTHY = 3;
  }

  Status status = 1;
  string version = 2;
}
```

## Adapter Interface Evolution

### New Adapter Interface

```go
// Adapter handles platform-specific messaging
type Adapter interface {
    // Lifecycle
    Initialize(ctx context.Context, config Config) error
    Start(ctx context.Context) error
    Stop(ctx context.Context) error

    // Message handling
    OnMessage(handler MessageHandler)

    // AI-specific capabilities
    Capabilities() AdapterCapabilities

    // Streaming responses
    StreamResponse(ctx context.Context, req *StreamResponseRequest) error

    // Status updates (loading states)
    SetStatus(ctx context.Context, conversationID string, status *StatusUpdate) error

    // Suggested prompts
    SetSuggestedPrompts(ctx context.Context, conversationID string, prompts *SuggestedPrompts) error

    // Thread management
    UpdateThreadMetadata(ctx context.Context, metadata *ThreadMetadata) error

    // Platform info
    GetPlatformName() string
    IsHealthy(ctx context.Context) bool
}

// Capabilities define what AI features the adapter supports
type AdapterCapabilities struct {
    SupportsStreaming       bool
    SupportsStatusUpdates   bool
    SupportsSuggestedPrompts bool
    SupportsThreads         bool
    SupportsTypingIndicator bool
    MaxUpdateRateHz         float64  // Rate limit for updates
    MaxContentLength        int
}
```

### Platform-Specific Implementations

**Slack Adapter**:
```go
capabilities := AdapterCapabilities{
    SupportsStreaming:       true,
    SupportsStatusUpdates:   true,   // assistant.threads.setStatus

    SupportsTypingIndicator: false,  // Slack doesn't have typing in assistant
    MaxUpdateRateHz:         0.33,   // 3 seconds minimum per Slack docs

}
```

```go
capabilities := AdapterCapabilities{
```

**Teams Adapter**:
```go
capabilities := AdapterCapabilities{
```

## Message Flow Sequences

### 1. Simple Message with Streaming Response

```
User types message in Slack
    ↓
SlackAdapter receives event
    ↓
Translate to proto Message
    ↓
Call gRPC ProcessMessage(msg)
    ↓
Agent receives message → stream
    ↓
Agent: Send StatusUpdate(THINKING)
    ↓
Messaging: SetStatus() → Slack API
    ↓
Agent: Send ContentChunk(START, "Hello")
    ↓
Messaging: Create Slack message
    ↓
Agent: Send ContentChunk(DELTA, " there")
    ↓
Messaging: Update Slack message (rate limited)
    ↓
Agent: Send ContentChunk(END, "!")
    ↓
Messaging: Final update to Slack
    ↓
Stream closes
```

### 2. Bidirectional Conversation with Cancellation

```
User starts conversation
    ↓
Adapter opens ProcessConversation stream
    ↓
Send ConversationRequest(message)
    ↓
Agent streams response chunks
    ↓
User clicks "Stop generating"
    ↓
Adapter sends ConversationRequest(feedback: CANCELLATION)
    ↓
Agent receives cancellation
    ↓
Agent stops generation, closes stream
```

### 3. Suggested Prompts Flow

```
User opens AI assistant (Slack)
    ↓
Slack fires assistant_thread_started event
    ↓
Adapter translates to Message (empty content)
    ↓
Send to agent via gRPC
    ↓
Agent responds with SuggestedPrompts
    ↓
Adapter calls slack.SetSuggestedPrompts()
    ↓
User sees prompt suggestions in UI
```

## Rate Limiting Strategy

### Adaptive Rate Limiter

Handle platform-specific rate limits intelligently:

```go
type AdaptiveRateLimiter struct {
    platform      string
    maxRateHz     float64
    lastUpdate    time.Time
    buffer        strings.Builder
    timer         *time.Timer
}

func (r *AdaptiveRateLimiter) SendUpdate(content string) {
    r.buffer.WriteString(content)

    // Debounce updates based on platform capabilities
    if r.timer != nil {
        r.timer.Reset(r.debounceInterval())
    } else {
        r.timer = time.AfterFunc(r.debounceInterval(), r.flush)
    }
}

func (r *AdaptiveRateLimiter) debounceInterval() time.Duration {
    // Slack: 3 seconds minimum
    // Discord: 0.5 seconds for smooth streaming
    // Teams: 1 second balance
    return time.Duration(1.0 / r.maxRateHz * float64(time.Second))
}
```

## Error Handling

### gRPC Status Codes

Use standard gRPC status codes:
- `OK`: Success
- `CANCELLED`: User cancelled operation
- `INVALID_ARGUMENT`: Malformed message
- `DEADLINE_EXCEEDED`: Timeout
- `RESOURCE_EXHAUSTED`: Rate limit exceeded
- `UNAVAILABLE`: Service down
- `INTERNAL`: Agent error
